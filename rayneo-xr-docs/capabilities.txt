1. Binocular Display​

To implement Binocular Display, in addition to duplicating the same UI layout on both the left
and right sides, any modification made to the left view must also be applied to the right layout.
These requirements introduce a significant amount of boilerplate code. To address this issue,
the SDK provides the BindingPair utility class based on ViewBinding. After passing the
ViewBinding objects corresponding to the left and right layouts to its constructor, you can:​
• Use the updateView method to operate on both layouts simultaneously.​
• Use the setLeft method to operate only on the left layout.​
• Use the checkIsLeft method within the updateView block to determine whether the
current operation is on the left or right layout.​

3. Touch Events & Event Response​

Currently, both left and right temple arms can trigger MotionEvent TP events. Unlike the 2D TP
events on mobile phones, TP events generated by the temple arms are 1D, with the X coordinate

changing dynamically and the Y coordinate fixed. In addition to the temple arms, ring
accessories (after pairing) also generate TP events.​
Event Response Mechanism​
When TP events are dispatched to the Activity or View level, the raw MotionEvent is passed to
the TouchDispatcher during the dispatch process. The TouchDispatcher converts
native TP events into gestures such as single tap, long press, double tap, triple tap, forward
swipe, and backward swipe (some gestures have default system sounds), which are exposed via
the CommonTouchCallback interface. Callers only need to implement business logic based
on these gestures.​
Based on TouchDispatcher and CommonTouchCallback , the following Activity-level
encapsulations are provided:​
• BaseTouchActivity : Automatically registers gesture listeners.​
• BaseEventActivity : Inherits from BaseTouchActivity and converts gestures into
Kotlin Flow event streams ( BaseMirrorActivity inherits from
BaseEventActivity ), mapping events to TempleAction subclasses. ​

4. Following Hand Effect (Smooth Scrolling)​
While the TouchDispatcher and CommonTouchCallback suffice for general scenarios,
achieving the smooth scrolling effect seen in mobile lists is challenging due to two main
limitations:​
1. Event Processing Layer: TouchDispatcher processes raw events into gestures, but
smooth scrolling requires direct handling of raw events.​
2. Coordinate System Mismatch: Raw TP events have a fixed Y-coordinate, while lists can be
horizontal or vertical and only respond to events within their bounds. This requires
dynamically adjusting coordinates:​
◦ Horizontal Lists: Modify the Y-coordinate based on the list's center.​
◦ Vertical Lists: Swap X and Y coordinates and fix the X-coordinate.​
Implementation Approach:​
• Continue feeding raw events to TouchDispatcher for gesture detection (clicks, taps, etc.),
but ignore forward/backward swipes.​
• Use a fixed focus position on the RecyclerView to intercept the raw event stream.​
• Generate new MotionEvent instances with adjusted coordinates, then feed them to the
RecyclerView and recycle them afterward.​
• The new event stream handles only scrolling, not click events.​
Three Common Scenarios:​
1. Fixed Focus + List Scrolling: Use RecyclerViewSlidingTracker .​
2. Moving Focus + List Scrolling: Use RecyclerViewFocusTracker with distance-based
focus changes.​

3. Moving Focus + Fixed View: Use FixPosFocusTracker .​
Key Logic for Moving Focus:​
After sliding a threshold distance (e.g., 50dp), trigger focus changes (forward/backward or
up/down) based on the swipe direction.​

5. 3D Effect Implementation​
In the Android native environment, a pseudo-3D effect is achieved using binocular parallax. The
core principle involves offsetting views in the left and right layouts in opposite directions to
create depth perception:​
• Left Layout: Views are shifted right.​
• Right Layout: Views are shifted left.​
• Varying offset values create different depths, resulting in a 3D effect when viewed through
both eyes.​

Sampling Rate Constant​
When registering a listener , you can choose different sampling rates:​
• SENSOR_DELAY_FASTEST : Fastest, with the highest possible frequency.​
• SENSOR_DELAY_GAME : Suitable for game rate.​
• SENSOR_DELAY_NORMAL : Default rate, suitable for screen orientation changes.​
• SENSOR_DELAY_UI : Suitable for User Interface changes.​
Best Practice: Always remember to call sensorManager.unregisterListener(this) in
onPause() to avoid background power consumption.​
